    shell with no distinguishing title.
  - `plan/CRITIQUE.md` pass 5 (2026-10-30, commit 879b69d): broadened — every named route (`/`, `/import`,

    shell pre-hydration; suggested the `web.output: "static"` config flip as the fix.
  - `/iterate` audit, same tick (2026-10-30, commit 35bf657): tried the suggested flip live. It is not a config
    flip. `expo export -p web` with `web.output: "static"` renders every route once in a Node (no-DOM) context;
    the root layout's providers assume a browser unconditionally. `src/lib/network.ts`'s top-level
    `createNetworkWatch({...})` call hits `expo-network`'s `addNetworkStateListener` eagerly at module load
    (`window is not defined`) — fixable with a `typeof window !== "undefined"` guard. But `PlayerProvider`
    (mounted root-wide in the layout, so every route gets it) calls `expo-audio`'s `useAudioPlayer`
    unconditionally at render time, reaching for the DOM's `Audio` global (`ReferenceError: Audio is not
    defined`) even on routes with no player UI (`/browse` was the one caught; the rest of the provider tree
    likely shares the root cause). Reverted both experimental edits — no code shipped.
- rationale: two independent critique passes plus a direct, reproduced technical investigation all point at the
  same root cause (the provider tree assumes a browser at module/render time, not just at effect time) rather
  than model imagination. This is exactly the "audit finding too big for one fix" shape expand exists to catch:
  `/iterate`'s own audit scored this 1.2 (impact 6, ease 2) and explicitly recommended `/plan-a-spec` over a
  third blind attempt, since fixing `PlayerProvider` alone may uncover further browser-only assumptions in
  storage/sqlite once it clears.
- proposed scope: unclear until scoped — likely 2+ chunks (make `PlayerProvider` defer `useAudioPlayer` to a
  client-only mount; audit the rest of the provider tree and `src/lib/` for the same eager-browser-API pattern;
  only then flip `web.output: "static"` and re-verify against expo-router's dynamic `[id]` segments).
- estimated chunks: 2-3 (provider audit is itself unscoped work)
- conflicts: none with spec.md non-goals. Tempered by `plan/bearings.md`'s own framing of the web build as "for

  listener-facing regression, which is why this sits here for `/oversight` to weigh against spec 01/05 product
  chunks rather than auto-promoting.
